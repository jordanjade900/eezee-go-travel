# EE-Zee Go custom operations backend

Built 9 October 2026. This is repository-owned code for registration, travel planning and staff management. It does not use a CRM subscription. Whop and all payment logic are explicitly deferred.

## Local use

Run `node tools/serve-operations.mjs` from the project root. The complete site and API are served on `http://127.0.0.1:4191`. On the first run, the server writes independent random secrets into ignored `.env.local` and a random local-only owner password into ignored `work/operations-access.md`. Passwords and tokens are never printed by the server. Keep those files private. Never deploy `.env.local` or the SQLite file.

`node tools/test-operations.mjs` exercises actual encrypted SQLite persistence, restart survival, access control, idempotency, status updates, private notes, itinerary versions, exact-version customer acceptance, concurrency, rate limits and adapter safeguards.

SQLite uses Node 24's built-in database module, WAL and `BEGIN IMMEDIATE` transactions. Only encrypted envelopes are written into the database. The dedicated server refuses hidden files and backend, tools, data, work, docs and dependency directories as static content.

## Production configuration

The Netlify function serves `/api/operations/*`. Set runtime function environment variables (not browser variables):

- `OPS_STORE=netlify`
- `OPS_ORIGIN=https://eezee-go-travel.netlify.app` (update when the canonical domain changes)
- `OPS_ENCRYPTION_KEY`: independently generated 32-byte hex secret
- `OPS_SESSION_SECRET`: independently generated 32-byte hex secret
- `OPS_ADMIN_EMAIL`, `OPS_ADMIN_NAME` and `OPS_ADMIN_PASSWORD_HASH` for first initialization

The password hash format is `32-hex-salt:128-hex-scrypt-hash`, generated by `hashPassword` in `security.mjs`. Once the store exists, the stored owner account controls authentication; changing the bootstrap environment hash does not reset its password. The authenticated owner can change their password in the staff workspace. No public password reset/email service is installed.

Encryption key changes require a planned decrypt/re-encrypt migration. Losing the key loses access to encrypted records. Rotating the session secret invalidates sessions AND customer tracking links because the same HMAC secret hashes both classes of tokens. Back up the secrets securely alongside database backups.

Production fails closed if keys or an HTTPS origin are missing. It never falls back to an ephemeral serverless SQLite file. The storage adapter uses a site-wide Netlify Blobs store with strong consistency, encrypted state and conditional `onlyIfNew`/`onlyIfMatch` writes; it retries conflicts up to eight times. A strict fetch wrapper refuses failed conditional PUTs before the SDK can mistake a non-412 error for success.

This initial low-volume operations store serializes writes through a single encrypted snapshot. It is deliberately not a financial ledger or seat-reservation database. Snapshot writes are capped at 15 MB. Before high traffic, large staff teams or a long history of requests, migrate to a transactional database and retain the HTTP contract. Netlify Functions/Blobs use the existing hosting infrastructure and its account usage limits; no paid CRM is required, but hosting is not an unlimited free service.

Official references used: [Netlify Blobs API and consistency](https://docs.netlify.com/build/data-and-storage/netlify-blobs/) and [Netlify Functions request context](https://docs.netlify.com/build/functions/api/).

## Saved workflow

Public forms create an encrypted durable registration or planning request. Submissions require consent, validated details, a UUIDv4 idempotency key and a honeypot field. A retry with the same key and same details returns the original reference and private token; changed details cause a conflict. Submission limits persist across process starts.

Each request receives a random reference and a separate 256-bit private access token. The reference is NOT a password. The access token expires after 180 days. New requests are assigned to the active staff member with the smallest open workload, or to the owner when there are no active staff. A follow-up date is set to the next calendar day in Jamaica; it is an internal default, not a promised customer response time.

Staff can filter requests, change status, assign work, set a follow-up date, save private notes, post customer-visible messages, and draft an itinerary. Internal notes and unshared itinerary drafts never appear in customer responses. Each draft increments the plan version; staff explicitly publish a version. Customers must accept the exact currently published version. Publishing the same version again preserves an existing acceptance. Publishing a revised version clears acceptance for the new version. Acknowledgement, itinerary approval and request status never represent paid/confirmed travel.

The owner can create departures and edit names, dates, advertised price text, included items, departure points, enquiry settings and informational capacity, add or disable staff, and export customer-data backups. Disabled staff sessions are revoked, and their open requests return to the owner. Each staff member can change their own password, which revokes their previous sessions. Staff sessions expire after eight hours and use HttpOnly, SameSite=Strict cookies; Secure is required in production. Mutation origin checks and authenticated role checks run on the server. Staff record revisions support optional quoted/unquoted `If-Match`; stale saves return HTTP 409.

Advertised trips seed from `data/local-trips.json`. Owner-created departures immediately appear in the live registration selector. Home and Group Trips load the same live catalogue, and Contact trip enquiries fetch current departure context. Owner edits update these views without a build. The original static flyer cards remain a crawlable failure fallback and are labelled as potentially outdated when live loading fails. Capacity is informational. `remaining` is always null because registrations do not reserve or confirm seats. Passed advertised departures reject new registration requests, and the owner may close enquiries. Prices retain their published text; no unverified currency/price-basis claim is introduced.

## What is intentionally deferred

- Whop checkout, payment webhooks, balances, refunds, deposit-driven seat confirmation.
- Email/SMS/WhatsApp sending. The system saves acknowledgements and customer-visible messages; it does not claim an email or message was delivered.
- Sensitive passport/visa document uploads.
- MFA, supplier integrations, automated supplier booking and public password recovery.
- Background email reminders: overdue summaries exist in the dashboard, but outbound reminders require a configured channel.
- Final client workflow rules, verified capacities, actual booking confirmation criteria and data-retention policy.

Do not remove those distinctions or invent client policies. The client is still providing written requirements.

## API summary

All JSON errors use `{ "error": "Human-readable message" }`; request bodies are capped at 32 KB. Responses are no-store. For POST/PATCH/PUT send `Content-Type: application/json` and use the website origin. Customer endpoints require `Authorization: Bearer <private token>`; staff endpoints use the HttpOnly cookie.

Public: `GET /trips`, `POST /requests`, `GET /request`, `POST /request/reply`, `POST /request/accept-plan`.

Staff: `POST /login`, `POST /logout`, `GET /session`, `GET /dashboard`, `GET /requests/:id`, `PATCH /requests/:id`, `POST /requests/:id/notes`, `PUT /requests/:id/plan`, `POST /requests/:id/plan/publish`, `POST /password`.

Owner: `POST /trips`, `PATCH /trips/:id`, `POST /staff`, `POST /staff/:id/disable`, `GET /export`. Export intentionally contains plaintext customer records for an owner backup and omits passwords, token hashes, access tokens, sessions and idempotency records. Handle downloaded exports as private customer data.
